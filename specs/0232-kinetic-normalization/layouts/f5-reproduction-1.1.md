**Writer.** In every commit the 1.1 file is the `--output` of RS:
- `main()` calls `json.dumps(result, indent=2, sort_keys=True)` and then `write_text`, or prints to stdout without `--output`. Lines: b:1666/1670, 31:1771/1775, f4:1850/1854, 68:1849/1853, 23:2984/2988.
- `result` is `_jsonable(summary)`. `_jsonable` (b:1189) converts ndarrays and tuples to lists and dict keys to `str`. It adds and removes no keys.
- At 239a3a7 only the legacy path writes 1.1 (see Group 4).

**Path notation**
- Dot-joined keys.
- `a[]` is an array level and `m.<map>` is a map key level.
- A parent object path is listed as a path, e.g. `counts` and `counts.favorable_polytopes`.
- An array key is listed bare (`a`). Its object elements contribute `a[].k`. No bare `a[]` entry is listed.
- A map node is listed bare (`m`) and in the map-node list. Object values contribute `m.<map>.k`. A nested map is declared as map node `m.<map>`. Scalar values add nothing below `m`.
- A list of lists normalizes its inner lists under a further `[]`. A list of lists of objects therefore gives `a[][].k`; a list of lists of scalars adds nothing.

**`[enc]` paths.** These are `.numerator` / `.denominator` paths under a value written by `_fraction_to_json` / `_phase_json`, which can be an int or `{numerator, denominator}`.
- Most are reachable.
- Paths tagged `[enc-only]` are statically unreachable, because the value is provably integral. I still list them in O, so a reader does not reject a file over an encoder branch. See Open points.

**Optionality.** Everything below an optional parent (null-able object, or array that may be empty or all-null) is O at the layout level. Inside a subtree, I mark keys that are always present with their parent as "with parent". Keys that are conditional within their parent carry their own citation.

**Macros.** Subtrees are written once as macros (`PROV`, `FROZEN`, ...) and mounted at a prefix. Each macro expands to `prefix.path` for every path listed. Expansion is mechanical.

**Conventions shared with the two 1.0 records**
- (a) No bare `a[]` or `m.<map>` entries (see Path notation).
- (b) `details[]` element keys that are always present in a non-empty `details` list are **required** in the `--keep-details` (K) layouts. These are the 14 keys from `details.append` (b:1390-1407) and PROVREC.
  - A file with `details: []` (zero loaded or sharded polytopes) has exactly the path set of the layout with the same A, D and M flags and K off. E is inert without K. That K-off layout covers it.
  - The K-on and M layout with zero records writes `model_stage.models: []`, which has the same path set as the K-off and M layout (`models: null`).
  - Keys under values that can be null or `[]` stay optional, for example `details[].trilayer.*`, `details[].h21_plus_zero_per_class[].*` and `model_stage.models[].*`.
- (c) `diagnostic.checks` holds fixed fields, not a map node (DIAG).
- (d) `--h11` values that change paths form separate layout families (see "h11 families"). This splits every group: G1-G3 into 2 families, G4 into 3.

## Open points

1. **Path convention.** I list no bare `a[]` or `m.<map>` entries; element and value keys appear as `a[].k` and `m.<map>.k`. The A2 text does not decide whether `a[]` itself is a path. If the 1.0 record or the reader uses a different convention, these records must be re-expressed in it before encoding.
2. **`schema_metadata.deprecated_aliases` is treated as a map node.** Its keys are alias paths that themselves contain dots (`counts.source_vertex_evidence_...`; b:110-117). As field names they would give ambiguous dotted paths. Decision needed.
3. **`terminal_ledger.terminal_status_counts` is treated as a map node** (a count by status). Its key set is fixed per ledger module: every `LEDGER_TERMINAL_STATUSES` entry is always written (TL:298-301). The same applies to `record_kind_counts` (data-dependent keys, a map in either case).
