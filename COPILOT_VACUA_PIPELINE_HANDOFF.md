# Copilot handoff: complete the `vacua-pipeline` branch

## Mission

Complete and publication-harden the vacua/minima pipeline on the
`vacua-pipeline` branch. The finished work must:

1. reproduce the results already generated by the repository's legacy and
   reduced-JLM code;
2. provide a deterministic, resumable, failure-tolerant production path;
3. preserve enough metadata to make every reported vacuum count auditable;
4. scale from the paper benchmarks through the available `h11=4:50` data and
   remain extensible to `h11>200` and `h11=491` geometries.

Do not work in, merge into, or rewrite the `spectrum` branch. The spectrum
work is complete elsewhere. At the start of every session, run:

```sh
git branch --show-current
git status --short --branch
```

The branch must be `vacua-pipeline`. If it is not, stop and ask the expert
before editing. Use the isolated worktree associated with this branch. Never
use `git reset --hard`, broad deletion, or an unreviewed HDF5 overwrite.

Read these files completely before making changes:

The project uses Julia matrices in the convention `Q :: (h11, instantons)`
and `L :: (2, instantons)`. The Python/Julia transpose boundary is a known
failure mode; do not reintroduce transposes into the geometry-level APIs.

- The full Julia test suite passes in the prepared vacua worktree.

Treat all numerical counts from finite-start Newton searches as search-budget

## Interaction protocol with the expert

Work in small, reviewable stages. After each stage, report:

- files changed;
- commands run;
- tests and numerical comparisons passed;
- remaining uncertainty;
- estimated runtime/memory impact.

Ask the expert before making a decision that changes scientific meaning,
including:

- changing the default threshold or normalization;
- changing the definition of `Nvac`, `N_min`, or multiplicity;
- changing the accepted residual/eigenvalue tolerances;
- replacing legacy results rather than adding a compatibility path;
- launching a large scan, using `--force`, or modifying source HDF5 files;
- claiming search completeness for a finite-start numerical method.

You may proceed without asking for ordinary read-only inspection, unit tests,
small synthetic fixtures, dry runs, and bounded pilot runs.

## Staged implementation plan

### Stage 0: establish a baseline

Run and save the output of:

```sh
julia --project=. test/runtests.jl
git diff --check
```

Run the paper checkpoints:

```sh
julia --project=. scripts/reproduce_2023_n8.jl
```

For any existing data directory, run a single explicit geometry in dry-run or
`save=false` mode before touching files. Record Julia version, git commit,
data root, threshold, starts, precision, and BLAS thread count.

### Stage 1: make the single-geometry API auditable

Review `compute_axion_data` and `save_axion_data` in
`scripts/vacua_pipeline.jl`.

Required behavior:

- validate the geometry file and matrix dimensions before numerical work;
- use one explicitly reported threshold for estimate and identification;
- expose search budget and residual tolerance as named options;
- distinguish `estimated`, `verified`, `failed`, and `not_applicable` states;
- record solver status, starts, residual tolerance, branch method, Julia
  version, git revision, and runtime in HDF5 metadata;
- never destroy an existing result unless `--force` is explicit;
- write to a temporary file/group and atomically finalize where practical;
- preserve legacy datasets and readers.

Add tests for malformed dimensions, legacy files, metadata round trips, and a
synthetic square geometry. Do not claim a finite-start search is complete.

### Stage 2: define the minima-search decision tree

Implement or document this order:

1. square/unimodular or determinant-certified leading problem: exact algebraic
   count where valid;
2. leading determinant-lattice branch enumeration using
   `leading_critical_branches`;
3. reduced-JLM solve using `jlm_reduced.prepare` once and repeated
   `jlm_reduced.minimize` calls where selected data can be reused;
4. bounded numerical critical-point search only when the preceding paths do
   not apply.

For every path, return method, count, multiplicity, residual diagnostics, and
whether the result is exact, certified for the selected branch set, or a
finite-search lower bound. Add cross-method tests on N=5, N=8, the Appendix C
geometry, and at least one non-square synthetic case.

### Stage 3: build a resumable batch runner

Extend or add a batch script, modeled on `scripts/batch_jlm_reduced.jl`, with:

- `--data-dir`, `--h11`, `--limit`, `--offset`, and repeated `--geometry`;
- `--threshold`, `--starts`, `--residual-tolerance`, and method selection;
- `--summary`, `--append-summary`, `--force`, and a dry-run mode;
- one CSV/JSON row flushed per geometry;
- per-geometry exception capture and continuation;
- skip logic based on matching pipeline version/configuration, not merely file
  existence;
- no shared HDF5 handle across workers;
- deterministic ordering and reproducible seeds if random starts are used.

Start with `limit=1`, then 10 geometries, then one complete h11 slice. Never
start the full `h11=4:50` scan without expert approval.

### Stage 4: reproduce existing repository results

The following comparisons are mandatory:

- N=5 critical/minima counts in `paper_benchmarks`;
- N=8 counts below/above the catastrophe (`5` and `1` minima);
- the six inflation-screen geometries and their leading branch counts;
- existing reduced-JLM CSV summaries under `data/logs/`;
- h11=4:11 aggregate statistics against
  `paper_benchmarks/2023_minima/h11_004_011_reduced_jlm_vs_digitized.csv`;
- exact selected-column ordering from the allocation-free selector on the
  known h11=10 and h11=20 checks.

For every discrepancy, save a small reproducer containing `(h11, polytope,
frst)`, Q, L, threshold, method, and solver diagnostics. Do not silently
adjust tolerances to force agreement.

### Stage 5: large-geometry and HPC validation

Benchmark representative geometries at `h11=150`, `180`, `200`, and when
available `400–491` using 1, 2, 4, 8, and 16 BLAS threads. Report wall time,
peak memory, allocations, physical-mode count, and provisional status.

Use hybrid parallelism only after the single-geometry benchmark:

```text
geometry workers × BLAS threads per worker <= allocated physical cores
```

Keep sparse accumulation separate from dense whitening/eigendecomposition in
the profile. Do not assume arbitrary-precision refinement scales with BLAS.
Use one writer per geometry and merge summaries in the parent process.

## Failsafes

- Default to no overwrite; require `--force` and print the exact target list.
- Validate `CYAXIVERSE_DATA_DIR` and refuse an empty/root-like target.
- Refuse to process a geometry if Q/L/K dimensions or orientation are invalid.
- Bound branch enumeration with `max_branches` and fail clearly if exceeded.
- Bound numerical starts and iterations; record timeouts as failures.
- Store intermediate results in a temporary path before finalization.
- Flush summaries incrementally and make reruns idempotent.
- Keep numerical failures separate from missing-data failures.
- Never delete legacy groups or rewrite spectrum data as part of a minima run.
- Run `git diff --check` and the full test suite before every handoff.
- Keep generated bulk outputs out of git unless explicitly requested.

## Definition of done

The branch is ready for publication review only when all of the following are
true:

- the full test suite passes from a fresh instantiated environment;
- single-geometry and batch APIs are resumable and provenance-complete;
- all mandatory paper/repository reproduction checks pass or have documented,
  explained discrepancies;
- exact, branch-certified, and finite-search results are clearly separated;
- a bounded h11=4:50 pilot completes without data corruption and produces a
  machine-readable summary;
- large-geometry benchmarks and thread-scaling results are recorded;
- no changes touch the completed `spectrum` work except through an explicitly
  reviewed merge or cherry-pick;
- the expert has reviewed the final diff, summary schema, and numerical
  interpretation before publication claims are made.

At completion, leave a final report in the checkpoint with commit hash,
commands, dataset manifest, pass/fail counts, runtimes, and unresolved caveats.
