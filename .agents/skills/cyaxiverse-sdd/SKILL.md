# CYAxiverse Specification-Driven Development

1. Read `AGENTS.md`, the governing Issue, any existing feature spec/amendments, and only the domain skills/material relevant to the task. `AGENTS.md` remains the repository constitution; this skill does not override it.
2. Classify work by semantic risk: `S0` trivial (no spec required), `S1` bounded engineering, `S2` scientific/durable contract, `S3` research programme composed of independently testable S1/S2 slices. A small change is S2 when it changes scientific meaning. If classification ambiguity could affect scientific meaning or a durable scientific/contract boundary, fail closed to provisional S2 pending clarification; ordinary engineering uncertainty alone does not force S2.
3. For S1-S3 work, locate the governing `specs/<id>-<name>/spec.md` and any approved amendments. If none exists, draft it before changing intended behaviour. An Issue is the intake/coordination object, not a substitute for the feature contract. For S1, `plan.md` and `tasks.md` are optional when complexity warrants them; S2 normally uses all three artifacts.
4. Draft requirements around observable behaviour and evidence. For S2 scientific work, separate source facts, implementation facts, empirical evidence, owner-approved conventions and inference; state what the work may and must not establish. Use EARS-style requirements only when they improve precision.
5. Keep a spec `draft` while normative intent is unresolved. For S2/S3 work, do not implement consequential behaviour until the relevant scientific choices are owner-approved. Approved S2/S3 specs must record durable approval provenance, including the required reviewer role and an `approval_ref` that identifies the reviewed revision or normative content. Stop rather than infer a normalization, basis, population/counting definition, acceptance criterion, physical interpretation or scientific schema.
6. After approval, derive `plan.md` and `tasks.md` when required by class/complexity. Map every normative requirement/gate to planned implementation and verification. Give each task one observable outcome, include its verification, and name escalation conditions. Do not create a GitHub Issue for every task; promote only independently durable, blocked, mergeable/reviewable or owner-decision-bearing work. `tasks.md` is execution/evidence-readiness decomposition, not authoritative PR merge/Issue/Project status.
7. Implementation may change technical details without re-approval when intent is unchanged. If investigation changes intended behaviour, update and re-review the spec before continuing the affected work.
8. Partial-gate PRs are valid. State exactly which requirements/gates the PR implements, explicit non-scope, scientific/API/schema/version impact, evidence, and remaining work. For S0, irrelevant SDD sections may be omitted or marked `N/A`. Do not imply completion of a parent spec from a partial deliverable.
9. Before S2 completion, converge approved spec/amendments ↔ plan ↔ tasks ↔ implementation ↔ tests/scientific evidence ↔ PR scope. Any unmet requirement remains explicitly incomplete or becomes additional work; checked-off tasks are not proof of spec satisfaction.
10. For S1-S3, the governing Issue is the primary GitHub Project work item; linked PRs normally provide implementation/integration/evidence rather than duplicate main-board WIP cards. PR-only S0 work may itself be a Project item.
11. During brownfield migration, do not assume the original Issue body is the latest contract. Reconstruct a concise chronological decision/supersession record and migrate the latest durably owner-approved, non-superseded normative intent. Preserve older wording as history; do not pretend newly introduced requirement IDs governed historical execution.
12. GitHub Issues and Projects track work state and relationships. The Project is the live visual map, not a competing authority or prose ledger. Merge state, Issue closure, current Kanban state and current review ownership belong in GitHub, not `tasks.md`.
13. Before any durable GitHub write derived from private chats, local agent sessions, local filesystem context, connected applications or private attachments, apply the publication boundary in `AGENTS.md`. Remove private conversation/share URLs and transcript dumps; absolute local filesystem/home-directory paths; local usernames, hostnames and machine/device identifiers; local Codex/agent/workspace/session paths; private attachment or connector-local locations; secrets, credentials and tokens unless the owner explicitly approved that exact datum for publication. Use repository-relative paths for repository content. If safety is uncertain, omit the datum and stop for owner direction.
14. Do not turn every chat into a Project card. Promote conversation-derived work only when it produces an independently durable project outcome such as a research question, decision, blocker, proposed spec, implementation follow-up or evidence-bearing investigation. The checkpoint is a sanitized summary, never a transcript. It may contain title/question, Workstream, normal Project Status/Priority, a public-safe conclusion, next action, related Issue/spec/PR or repository-relative references, and optionally an opaque non-resolving private reference. Never publish a resolving private-chat or local-machine locator. Conversation checkpoints use the existing Project lifecycle and governing-Issue model; a `Research & Chats` view is only another view over the same Project items, not a second ledger or status system.

Finish with the governing spec/status, approval provenance where required, requirements/gates advanced, verification evidence, remaining work, and any owner decision required. Use the relevant domain skill as well when the work changes Julia/scientific/sampling/vacua/release behaviour.
